## 2. 逐条回答 Issue 的七个检查项

### 2.1 M=1 是否有合法分派

**分派合法（不报错），但落点是一个 64 行 tile，不是 GEMV。**

三道事实：

**(a) trellis 在 dispatch 层无条件进 GEMM。** `matmul_metal_kernel.rs:97`（`choose_dispatch`，main 分支，PR #900 未触碰）：

```rust
if shape.b_is_trellis {
    return MatmulDispatch::Gemm(problem.select_plan());
}
```

在 `qmv::route` 与 `GemvSpecialization::select_shape` 之前就 return 了，M=1 也一样。

**(b) GEMV 侧显式拒绝 trellis。** `gemv/kernel.rs:436`：

```rust
MatmulB::Trellis { .. } => {
    return Err(MatmulMetalError::UnsupportedLayout { path: "Gemv" });
},
```

`gemv/` 下 16 个文件，`qmv/routes.rs`（16.6 KB）里 `trellis` 出现 **0 次**。

**(c) 落到哪个 tile。** PR #900 新增 `select_trellis_tiling`：

```rust
fn select_trellis_tiling(m: u32, n: u32, engine: GemmEngine) -> GemmTiling {
    match engine {
        GemmEngine::Simdgroup => GemmTiling::Tile64x64x32_Simdgroups2x2,
        ...
```

`Tile64x64x32_Simdgroups2x2` **不是为 trellis 新造的**，它在 main 的 `gemm_tiling.h` 里早已存在（`block_m=64, block_n=64, block_k=32`），是量化路径的既有 tiling。

**所以 M=1 的路径是：1 行激活 × 64 行 tile。** 代价见 §4。

PR 的测试确实覆盖了 M=1（`trellis_gemm_test.rs` 新增 `(1, 6, 5120)` 与 `(1, 80, 5120)`，且删掉了 `if !context.supports_mxu { return; }` 的提前退出）。**设计意图是认真的，只是没编译过。**

### 2.2 非 MXU 是否避开 MXU gate

**是，两道闸都拆了。** 这是 PR #900 唯一真正完成的改动。

**闸一（选路）。** main `selection.rs:55-56`：

```rust
if self.shape.b_is_trellis {
    return select_trellis_plan(self.shape.m, self.shape.n, self.shape.k);
}
```

`select_trellis_plan`（main:152）硬编码 `engine: GemmEngine::Mxu`（main:176）。PR #900 **整个删掉了这个函数**，改为走通用路径：

```rust
- if self.shape.b_is_trellis {
-     return select_trellis_plan(self.shape.m, self.shape.n, self.shape.k);
- }
  let engine = if self.supports_mxu && mxu_is_eligible(self.shape) {
      GemmEngine::Mxu
  } else {
      GemmEngine::Simdgroup   // ← M4 落这里
  };
```

**闸二（编码）。** main `trellis.rs:67`：

```rust
if plan.engine != GemmEngine::Mxu
    || !arguments.output.ops.mask().is_empty()
    ...
{ return Err(unsupported()); }
```

PR #900 改为：

```rust
if (plan.engine == GemmEngine::Mxu) != tiling.is_mxu_variant()
    || ...
```

即"engine 与 tiling 必须一致"，而不是"engine 必须是 MXU"。

**新增的两条约束（不是 gate，但要记）：**

- `split_k` 计算里 `if !shape.n.is_multiple_of(4) { return 1; }` —— 只关掉 split-K，不影响可执行性。
- `TrellisGemm` 的 kernel cache key 从 `(tiling, format, alignment)` 扩成 `(tiling, use_mxu, format, alignment)` —— 这是必要的，否则同 tiling 的 MXU / Simdgroup 变体会互相覆盖。

### 2.3 shader 依赖

**新增了一个可用依赖，但保留了一个可能致命的头文件依赖。**

**(a) 新增的 Simdgroup 路径是真的 simdgroup_matrix。** `gemm_trellis.metal` 新增 `#include "../common/simdgroup_fragment_ops.h"`，`SimdgroupFragmentOps::FRAGMENT_ROWS/COLS` 直接取自 `SIMDGROUP_MMA_ROWS/COLS`，而 `simdgroup_multiply_accumulate.h:10-11` 定义 `SIMDGROUP_MMA_ROWS = 8, COLS = 8`，`:36` 是 `metal::simdgroup_matrix<AccumulatorT, ROWS, COLS>`。

**这条同时再次确认 R3 的 E-8**：M4 有 `simdgroup_matrix`，不是 M5 专属。

**(b) 但 `#include "common/mxu_mma_core.h"` 保留了，且没有版本守卫。** 传递链：

```
gemm_trellis.metal
  → gemm/common/mxu_mma_core.h          (260 行，无 __METAL_VERSION__ 守卫)
    → common/mxu_fragment/ops.h:24      using MatmulMode = mpp::tensor_ops::matmul2d_descriptor::mode;
    → common/mxu_fragment/fragment_matmul.h:25
                                        mpp::tensor_ops::matmul2d<descriptor, metal::execution_simdgroup> matmul_op;
```

`mpp::tensor_ops::matmul2d` 是 **Metal Performance Primitives 的 tensor ops**，也就是 Metal 4 / M5 NAX 那套 API。整条链上 grep `__METAL_VERSION__` 与 `#if` **零命中**。

**后果（E2，推断）**：`if constexpr (USE_MXU)` 只裁剪**代码**，不裁剪**头文件**。Metal 编译器在 Metal 3 工具链上会因找不到 `mpp::tensor_ops` 而整个 translation unit 失败——即使运行时永远走 Simdgroup 分支。

**这条我没有验证，因为本机没有 Metal 编译器**（见 §6）。要验证它，只需要一条命令：在只有 Metal 3 SDK 的机器上 `xcrun -sdk macosx metal -c gemm_trellis.metal`。

### 2.4 状态位宽与激活量化

**格式（E1，来自 `trellis.h` 与 lalamo PR #364 的正文）：**

| 常量 | 值 | 含义 |
|---|---|---|
| `STATE_BITS` | 16 | 每 restart 块一个 16-bit 起始状态 |
| `WEIGHTS_PER_DECODE` | 4 | 一次 `decode_biased_weights` 出 4 个权重（一个 uint32 的 4 个字节） |
| `MAX_BIASED_WEIGHT` | 111 | `8*12 + 15`，level ∈ [0, 111]，7 bit 量级 |
| `WEIGHT_BIAS` | 54 | 全非负编码的偏置，epilogue 减掉 |
| `K_STEP` | 64 | 外层 K 步长 |
| `HASH_MULTIPLIER` / `INCREMENT` | `0xCFCCB83F` / `0x584B4AA3` | 码本 hash 生成，零查表 |

三种格式的 bpw 与 `K_STEP` 的关系（R3 已算，此处保留）：`V4_T8` = 2.125、`V2_T4` = 2.004、`V2_T6` = 3.004。

lalamo PR #364 正文补充了两个 R3 没记的细节（E1）：

> "QTIP uses MSB-first trellis codes, **one folded float32 scale per output row** and a five-float codebook. V2 supports 4/6/8-bit transitions; V4 supports connected T8 and T6/T7/T8 with 64- or 128-column restarts. **Restart blocks are contiguous in bits, with 16-byte row alignment.**"

"每输出行一个 fp32 scale" = 32 bit / 行。对 K=5120 的行是 32/10240 = **+0.3%**，所以 V2_T4 的 2.004 而不是 2.000。**这个开销不是零，R3 的"2.004 bpw"已经含它，但没说清来源。**

**激活（E1）：int8 对称，且需要 3 个 buffer。** `trellis.rs` 的 `encode_plan` 开头解构 A 操作数：

```rust
let (MatmulA::Int8Symmetric { activations, scales: activation_scales,
                              group_sums: column_group_sums, .. },
     MatmulB::Trellis { codes, row_scales, codebook, format }) = (arguments.a, arguments.b)
```

每 token 的输入侧成本：int8 值 + fp32 per-token scale + **fp32 column group sums**（每 4 列一组的部分和，供 `WEIGHT_BIAS` 修正用）。第三个 buffer 是 uzu 特有的，MLX / llama.cpp 都没有对应物。

**非 MXU 路径的实现方式（E1，这是本轮最重要的机制发现）：**

```metal
} else {
  // Decode B to threadgroup, MMA in float, accumulate in int.
  ...
  *reinterpret_cast<threadgroup bfloat4*>(b_shared + row_offset * B_SHARED_STRIDE + column) =
      bfloat4(float4(as_type<uchar4>(biased_weights)));
  ...
  uzu::matmul::Fragment<float, TILES_M, TILES_N, Ops> slab_products;
  uzu::matmul::fragment_mma(slab_products, left_tile, right_tile);
  slab_products.zip_for_each_coord(..., [&](short, short, thread float& slab, thread int& exact) {
      exact += int(slab);
  }, slab_products, products);
}
```

三件事同时发生：

1. **B 被物化到 threadgroup**（`b_shared`，`BLOCK_N × (BLOCK_K + 8)` bf16 = 64×40×2 = **5,120 B**），不是内核内直算。这就是 Issue 主题①问的"是否 materialize"——**是**。
2. **MMA 用 float**（`Fragment<float, ...>`），不是 bf16。Apple 的 `simdgroup_matrix<float,8,8>` 在 fp32 上没有专用矩阵单元，等价于走 ALU。
3. **累加回 int32**（`exact += int(slab)`）。

第 3 点带来一个**R2/R3 完全没提到的精度约束**：

```metal
static_assert(USE_MXU || BLOCK_K * MAX_ACTIVATION_MAGNITUDE * MAX_BIASED_WEIGHT < FLOAT_EXACT_INTEGER_LIMIT,
              "BLOCK_K slab must sum exactly in float");
// MAX_ACTIVATION_MAGNITUDE = 128, MAX_BIASED_WEIGHT = 111, FLOAT_EXACT_INTEGER_LIMIT = 2^24
```

BLOCK_K=32 → 32×128×111 = 454,656 < 16,777,216 ✓。含义：**float slab 的求和必须保持整数精确**，否则 int 累加就错。这把 `BLOCK_K` 与激活幅度绑死：若把 BLOCK_K 提到 1024，上限变成 1.45e7，已贴近 2^24，**任何激活幅度上浮都会溢出**。

**这是一条真实的、可移植的工程约束**：低位宽 + int 累加 + float MMA 三者组合时，slab 大小不是自由参数。

## 4. 定量：M=1 走 64 行 tile 的真实代价

这一节只用 tile 形状与 MAC 计数，**不依赖任何未验证的硬件常数**。

**参数**（`gemm_tiling.h` + `simdgroup_fragment_ops.h`）：

- `BLOCK_M = 64`，`BLOCK_N = 64`，`BLOCK_K = 32`
- `SIMDGROUPS_PER_ROW = 2`，`SIMDGROUPS_PER_COLUMN = 2` → `SIMDGROUP_BLOCK_M = 32`，`SIMDGROUP_BLOCK_N = 32`
- `FRAGMENT_ROWS = FRAGMENT_COLS = 8` → `TILES_M = 4`，`TILES_N = 4`，`TILES_K = 4`

**每 k-slab 的 MAC 数**：

```
MMA MACs   = BLOCK_M × BLOCK_N × BLOCK_K = 64 × 64 × 32 = 131,072
M=1 有用     =   1 × 64 × 32             =   2,048
冗余倍数     = 64×
```

**换算成"每有用权重多少 ALU op"**（1 MAC = 2 op）：

```
ops/weight = 2 × (BLOCK_M / M) = 2 × 64 / 1 = 128 ops/weight
```

**对照 R3 的带宽–ALU 预算**（`2026-10-r2-kernel-matrix.md:168`，以 124.6 GB/s 派生值为自变量）：

| 假设带宽 | 预算 |
|---|---|
| 124.6 GB/s（派生） | 6.7 ops/weight |
| 190 GB/s | 4.4 ops/weight |
| 273 GB/s（规格峰值） | 3.1 ops/weight |

```
128 / 6.7 ≈ 19×   ← M=1 超预算 19 倍
```

**crossover**：`2 × 64 / M ≤ 6.7` → `M ≥ 19.1`。即

> **M ≳ 20 时，这条 Simdgroup trellis 路径回到 ALU 预算内；M = 1 需要 128 ops/weight，是预算的 19 倍。**

**这条结论的含义，比"没测过"更重要：**

1. **PR #900 的价值区间是 prefill，不是 decode。** M=64 时 tile 打满，ops/weight = 2，远低于 6.7 的预算 → 这时 2 bpw 的字节收益**有机会**兑现。
2. **M=1 是结构性劣势，不是调参问题。** 要修只能写 trellis GEMV（一次 decode 只算 1 行），而不是把 64 行 tile 换个 tiling。而 `gemv/kernel.rs:436` 明确拒绝 trellis，#900 也没碰它。
3. **这与 R3 的 ALU 预算分析是两条独立路径得出同一结论**：R3 从"2 bpw 需要多少 ALU"推出"非 MMA 路径吃紧"；本轮从"tile 形状 × M"推出"decode 需要 19 倍预算"。**互相印证，不是同一论证的重复。**

**反面证据（必须写进来）**：上述 128 ops/weight 假设 MMA 的 M 维浪费直接等于 ALU 浪费。如果 Apple 的 fp32 `simdgroup_matrix` 在硬件上做了 M 维短路（我没有任何证据表明它做了），实际会低于 128。**这是 E2，不是 E0。**

---

## 5. 与 R3 结论的关系：方向不变，理由要改一处

R3 的裁决是"**不做 trellis 移植**"，理由是"**最好的公开实现主动要求 M5，而不是降级到非 MMA 路径**"。

现在这句话要改：

| | R3 的表述 | R4 核实后 |
|---|---|---|
| 门禁 | `select_trellis_plan` 硬编码 `GemmEngine::Mxu`，M4 上 `MxuUnavailable` | **门禁在 PR 里被删了**（两道都删），但 PR 编译失败、draft、冲突 |
| 非 MXU 路径 | 不存在 | **存在**（decode→threadgroup、fp32 MMA、int 累加），但**从未编译通过** |
| 理由 | "主动要求 M5" | "**非 MXU 路径当前不可编译；即便修好，M=1 走 64 行 tile，算术量是预算的 19 倍**" |
| 结论 | 不做移植 | **不变**，但证据从"设计意图"换成"编译失败 + 结构分析" |

**新增的一条结论（R3 没有）：** trellis 在非 MXU 上只可能对 **prefill** 有意义。R3 说"ALU 预算紧"，本轮把它定位到了具体区间：**M ≳ 20**。这意味着如果将来有人要做，正确的切入点不是"让 trellis 在 M4 上跑起来"，而是"**给 prefill 做 trellis，给 decode 保留 4-bit GEMV**"——两个 kernel，两种格式，一次权重两份存储，这在 24 GB 上不成立。

## 8. 本轮新增的三条可复用结论

1. **"门禁被删"与"路径可用"是两件事。** 判断上游支持度，必须查到 **CI 在目标平台上的结论**，而不是读 diff。这个 PR 的 diff 看起来完全正确，CI 显示它在第一个 shader 上就断了。
2. **`if constexpr` 裁不掉 `#include`。** 一个"运行时按设备分支"的 kernel，如果两个分支的头文件都无条件包含，那么它实际要求的是**两个分支的 API 全集**。uzu 的 trellis shader 因此仍然要求 Metal 4 MPP。
3. **低位宽 + int 累加 + float MMA 会把 `BLOCK_K` 变成精度参数。** `BLOCK_K × max|a| × max|w| < 2^24` 这条 static_assert 是可移植的工程约束，任何"decode 到共享内存再 MMA 累加回 int"的设计都会撞上。
