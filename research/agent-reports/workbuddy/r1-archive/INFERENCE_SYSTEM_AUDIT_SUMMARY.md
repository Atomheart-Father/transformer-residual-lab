# 摘要：消费级硬件 LLM 推理系统审计（v1）

**完整报告**：[`docs/INFERENCE_SYSTEM_AUDIT.md`](INFERENCE_SYSTEM_AUDIT.md) · 2026-10-21
**边界**：无新增 GPU 基准、无模型下载、无核心库改动、无提交。全部数字标注 E0/E1/E2/E3/E4。

## 一句话

**「压缩关键路径深度」这条路在 M4 Pro 上已经走到头了；能兑现的加速在「每 token 字节数」和「调度」，不在「依赖图」。**

## 五个关键判断

1. **decode 的真实瓶颈是 46% 的访存效率。** 880.8 MB 权重 ÷ 7.07 ms = 124.6 GB/s（峰值 273）。不是锁，不是「GPU 忙」，也不是「深度太长」——28 个 Block 的权重必须每步读一遍，DAG 不改变字节数。
2. **prefill 的端到端算力只有 2.06 TFLOP/s**（单 Block 孤立测 3.4）。`mx.compile` 只带来 2.4%，说明 dispatch 不是主要成本，GPU 确实在算——只是 M4 没有矩阵核。
3. **mlx-lm 的四个特性是互斥的**：KV 量化 ✗ 连续批处理、KV 量化 ✗ 滑窗、连续批处理 ✗ 投机解码、批处理 ✗ `keep>0`。全部有源码行号。
4. **投机解码是唯一能减少 bytes/token 的机制**，因此是 Apple Silicon 上唯一有结构性收益的 decode 路径。draft 同尺寸时 100% 接受率才打平；draft 小 10×、接受率 70% 时约 2.1×。
5. **长上下文是两段式灾难**：32k 时 decode 由 KV 带宽主导（3.5 GiB > 0.86 GiB 权重），prefill 由注意力二次项主导（152 TF 中 123 TF 是注意力）。128k 的 KV（14 GiB）超过单 buffer 上限（13.32 GiB）。

## 五个机会（按证据强度 × 成本排序）

| # | 机会 | 预期 | 成本 | kill 条件 |
|---|---|---|---|---|
| O1 | decode GEMV 带宽/占用率 | 1.15–1.4× | 3–5 天 | 手写与现成 kernel 差 <10% |
| O2 | KV 分页 + 融合 quantize-append | 峰值 −40%，32k +20% | 2–3 周 | 单请求无改善 |
| O3 | 小 draft / prompt-lookup 投机解码 | 1.4–2.1× | 1–2 天（零新模型） | 接受率 <30% |
| O4 | Radix 前缀缓存 + 零拷贝 | 多会话 TTFT −70% | 5–8 天 | 4 会话改善 <20% |
| O5 | prefill 融合（SwiGLU/RoPE） | 3–8% | 3–5 天 | 2048 token 下 <2% |

**明确不推荐**：继续压缩深度 / 稀疏 DAG（两轮否证）、ANE 跑 decode、M4 追张量核、现在做专家流式卸载。

## 需要批准的三件事（都很轻）

- **X1** 同进程交替测 28-block 链与单 Block + `powermetrics`：定位 1.9× 差异。5–8 min GPU。
- **X2** 合成张量 GEMV/GEMM 扫描（M×K×N×dtype）：建立 roofline，不下载模型。15–20 min GPU。
- **X3** prompt-lookup 投机解码：验证接受率。10–20 min GPU。

## 请三方重点裁决的五个问题

1. 46% 带宽里，「kernel 太小」与「DRAM 并发不足」各占多少？X1/X2 能否判定？
2. 「深度不是延迟」这个结论在 batch>1 或 M5 上是否仍然成立？（我们判断：decode 成立，prefill 不成立。）
3. KV 分页在单用户开发机上是否值得 2–3 周？还是「预分配 + 几何增长」两天方案就够？
