## 1. E-R5-1（P0）质量参照：我把"比较判据"写成了"有效性判据"

### 1.1 R4 原文

`2026-10-r4-experiment-readiness.md:174`：

> **参照必须是同 checkpoint 的另一种编码，不是 BF16。** 0.6B 上 BF16 与 2-bit 的差距（R2 记录为 ~0.77 nats / 20.7%）会把编码差异完全淹没。BF16 只用作 L0 的数值真值。

### 1.2 错在哪

**错误一（逻辑）：把两个不同问题合并成一条规则。**

| 问题 | 需要的参照 | BF16 是否必要 |
|---|---|---|
| (a) 这个编码有没有损伤原模型？ | BF16（金标准） | **必要** |
| (b) 两个编码之间谁更好？ | 彼此配对 | 不必要 |

R4 用 (b) 的答案去否定了 (a) 的参照。审查意见指出的正是这一点：**只做 Q2 vs Q4，无法排除"两者都严重损伤原模型"**。这个反驳成立。

**错误二（数字误植，我方自查）：那个 0.77 nats 根本不是 BF16 与 2-bit 的差距。**

0.766 nats / 20.7% 在我的记录里对应的是**关闭补偿器**的代价（wikitext `test_v2` 上关掉补偿器损失 20.7% ≈ 0.766 nats），属于"补偿器不跨语料"那条结论，与"BF16 vs 2-bit 量化差"没有任何关系。

本轮我在 `results/` 下用 `grep -rn "0.766\|20\.7"` 复查，**未能在已提交的结果文件里重新定位到该条目**（它只存在于 `stage1_8` 的叙述层）。因此：

- 该数字**不得**作为 BF16 与量化差距的证据；
- 也**不再**作为任何判据的依据；
- 正确表述是：**BF16 与 Q2 的差距在本项目里从未被测量过。** 这恰恰是审查要求补 BF16 参照的最强理由——不是"差距太大所以要排除 BF16"，而是"差距未知，所以必须测"。

### 1.3 修正后的表述（替换 R4 §4.0 第 1 条）

> **参照是三方，不是两方。** 同一 checkpoint 的 **BF16**（金标准）、成熟 **Q4**（可接受的损伤标尺）、候选 **Q2**（被测对象），三者在同一批窗口、同一 token 数上各跑一遍，全部配对。
>
> - **BF16 回答"有没有伤到原模型"**；没有它，Q2 与 Q4 的差值只说明两者之间的相对优劣，**不能排除整条阶梯都已越界**。
> - **Q4 提供损伤的量纲**：把 Q4 相对 BF16 的差值当作"可接受损伤"的经验标尺，Q2 的额外损伤与它相比，才有可解释的尺度。
> - **Q2 vs Q4 是决策量**：它决定选哪个编码。
>
> 三者不是三次独立测量：配对均值下恒有 `Δ(Q2,Q4) = Δ(Q2,BF16) − Δ(Q4,BF16)`。三条都报是为了可读与交叉校验，**决策量是那个差**。

### 1.4 审查提出的降级条件，本项目不触发

审查写"若原 BF16 无法加载，必须将相关结论标成'仅相对 Q4'"。

**本项目不触发这个降级**：`mlx-community/Qwen3-0.6B-Base-bf16`（rev `e8e73ff3…`）就在本地 HF 缓存里，1.2 GB，加载无成本。Stage B 侧也能用 `convert_hf_to_gguf.py --outtype bf16` 产出同精度 GGUF（若该版本不支持 `bf16` outtype，则用 `f16` 并在报告里显式声明这一处差异）。

**所以"仅相对 Q4"这个标签在本轮不应出现。** 如果它出现了，说明 BF16 那一遍没跑，那是缺陷，不是限制。

## 2. E-R5-2（P1）256 MiB 是基准策略，不是硬件阈值

### 2.1 原文与真实出处

`uzu` 的 `crates/uzu-engine/unit/BENCHMARKS.md:116-119`，整节标题是 **"Cold GEMV"**：

> GEMV-class benches cycle through enough quant-buffer copies to cover a 256 MiB weight working set before reusing one.
> This avoids ranking kernels on cache-warm weights; pools allocate lazily, so criterion filters skip their cost.

**读法：机制是"轮转足够多份 quant buffer 副本，使同一个 buffer 在被复用之前已经过了 256 MiB 的读取"。** 256 MiB 是作者为自己的张量规模选的覆盖量，是**避免缓存热态排序的测试规范**，不是"低于 256 MiB 则测量无效"的硬件定理。

R4 `:115` 把它写成"**必须** ≥ 256 MiB，否则测的是 SLC 带宽"，`:164` 又升级成"**任何 GEMV 计时，working set < 256 MiB 一律无效**"。**这是把策略当定理，我接受这条批评。**

### 2.2 附带承认：R4 §2.4 的"系统性偏袒"缺依据

R4 断言"2-bit 的 173 MB 有一部分可能驻留 SLC，4-bit 的 319 MB 更彻底地打到 DRAM"，进而说这"正好是 R>1.05 最可能的来源之一"。

**Apple 未公开 SLC 容量**，我无法计算 173 MB 是否驻留。所以那句话在当时就没有依据，不是"结论对但表述过强"，而是**结论本身不成立**。撤回。

同时接受审查的另一半：**2-bit 与 4-bit 张量大小不等本身就是优化目的**。任何"把两者 working set 弄成一样大"的做法，都会把待测效应（少读字节）直接抹掉。

### 2.3 修正后的规则

把"working set 下限"换成"**复用距离下限 + 单次读取字节保持不同**"：

```
处理（treatment）：每次迭代实际读的字节 = 该编码的真实权重字节（2-bit 就是 173 MB，不放大）
控制（control）：同一 buffer 被再次读取之前，中间至少流过 R 字节

选 k 份副本轮转，使 reuse distance = (k-1) × size ≥ R
R 取 512 MiB（Apple 未公开 SLC；按"远大于任何合理 SLC 估计"取，并在报告中写明这个假设）
```

0.6B 上的具体取值：

| 编码 | 单份字节 | k | 实际 reuse distance | 总占用 |
|---|---|---|---|---|
| IQ2_XS (2.3125 bpw) | 173 MB | **4** | 3 × 173 = **519 MB** | 692 MB |
| IQ4_XS (4.25 bpw) | 319 MB | **3** | 2 × 319 = **638 MB** | 957 MB |

两者 reuse distance 都 ≥ 512 MiB，总占用都在 1 GB 以内——**不需要 29k×29k 的合成巨矩阵**。R4 的"方案 B2"（`N=K=30500`，fp32 参考 4.6 GB）与 Stage A 的"`N=K=29300`"**一并撤回**。

### 2.4 冷/热两组不是要消除的污染，是要报的结果

- **冷组**：按上表轮转副本。
- **热组**：同一 buffer 反复读。
- **`热/冷` 比值本身就是一个观测量**：它给出该编码在该尺寸下的缓存敏感度。若 2-bit 的热/冷比显著高于 4-bit，那才是"缓存偏袒"的**证据**；若两者接近，则 R>1.05 与缓存无关，必须去找别的解释。

这条把 R4 的"污染项"变成了"可检验的假设"，比直接排除更有信息量。

### 2.5 关于计数器

审查要求"有则用"。本机没有公开的 DRAM 计数器接口：`mx` 不暴露内存控制器计数，`powermetrics` 给的是 GPU 功耗与利用率，不是 DRAM 字节。**所以本项目不能声称"实测 DRAM 带宽"**——这与 C-01/E-10 已定的 `BW_derived` 命名一致，此处只是把"为什么拿不到计数器"写清楚。

### 3.2 结论：R4 §2.3 的命令不可运行

R4 `:100-102` 写的是：

```bash
python convert_hf_to_gguf.py <mlx_model_dir> --outfile qwen3-0.6b-f16.gguf --outtype f16
llama-quantize qwen3-0.6b-f16.gguf qwen3-0.6b-iq2xs.gguf IQ2_XS     # ← 这里会 throw
llama-quantize qwen3-0.6b-f16.gguf qwen3-0.6b-iq4xs.gguf IQ4_XS     # ← 这条合法
```

**`IQ2_XS` 那条会直接退出，不产出文件。** 不是"质量会差"，是"根本拿不到文件"。所以 R4 的 Stage B 准备清单**少了一整条依赖链**，而且缺的那条不是可选的。

这也解释了为什么审查把它标 P1 而我接受升级为 P0：**我交付的是一份不可执行的流程。**

### 3.3 缺失的依赖链（新增 P6/P7）

```
P6  build/bin/llama-imatrix                 → 与 P2/P3 同一次 cmake 构建
P7  calibration-data.txt                    → 本地无原始语料，需下载（约 12 MB）
```

`tools/imatrix/README.md`：

所以正确顺序是**四步**，不是三步：

```bash
# 2 算 imatrix —— 注意：模型必须是同一份 bf16/f16 GGUF

# 3 量化，两个格式共用同一份 imatrix
llama-quantize --imatrix imatrix.gguf qwen3-0.6b-bf16.gguf q2.gguf IQ2_XS
llama-quantize --imatrix imatrix.gguf qwen3-0.6b-bf16.gguf q4.gguf IQ4_XS

# 4 字节从文件读，不用名义 bpw
stat -f%z q2.gguf q4.gguf
```

### 3.4 一个审查没提、但很重要的公平性问题

**IQ4_XS 不要求 imatrix**（不在上面那个 switch 的列表里），IQ2_XS 要求。如果只给 Q2 配 imatrix，就是**给低比特开了小灶**，质量对比会系统性偏向 Q2。

**公平协议：两种格式使用同一份 `imatrix.gguf`。** 这样 imatrix 只作为"同一套校准信息"，不构成格式间的不对等。

但要注意：imatrix 会改变 `llama_tensor_get_type` 的分层决策（`llama-quant.cpp:688` 一带对前 `n_layer/8` 层按 `has_imatrix` 走不同分支），**所以两个文件的实际张量类型组合与字节数都会变**。这正是 R4 已写死的"C3 字节口径必须用实测文件大小"的必要性所在——名义 bpw 在 imatrix 介入后更不可靠。

### 3.5 校准集与评测集的隔离（审查要求）

- imatrix 用 `wikitext-2-raw` **train** 切出的连续文本块；
- 评测用本地 `data257/` 的窗口（来自 wikitext-2 **test** 切分，`data/data_manifest.json` 有 sha256）；
- **断言不相交**：按文档 ID 与字符区间双重检查，不能只比哈希。train/test 在 wikitext-2 里本来就是不同文档集，但仍要落一条断言，不能"理应如此"就跳过。

### 3.6 好消息：imatrix 与 quantize 都不需要 Metal 编译器

`llama-imatrix` 与 `llama-quantize` 是 CPU 路径。用 `-DGGML_METAL=OFF` 就能构建，**不需要 7 GB 的 Xcode**。

这把 Stage B 拆成两半：

| 子阶段 | 需要什么 | 能回答什么 |
|---|---|---|
| **B-quality**（本地可做） | cmake + clang（已装）+ `llama-imatrix`/`llama-quantize`（CPU 构建）+ 12 MB 校准语料 | IQ2_XS 在**正确 imatrix 流程**下能否编码、字节多少、NLL 差多少 |
| **B-speed**（本地做不了） | **`xcrun metal`**（需 Xcode） | M4 Metal 上的 IQ2_XS vs IQ4_XS 兑现率 |

**B-quality 不依赖 Xcode。** 这是本轮对 R4 "Stage B 三项缺口"的实质修正：缺口仍是三项，但**质量那一半可以先做**，且它恰好是审查最关心的部分（"不能把无效流程当公平流程"）。

## 4. E-R5-4（P2）L0 不能靠"比 Q4 差"否决

### 4.1 R4 原文与问题

`2026-10-r4-experiment-readiness.md:235`：

> 不是加权打分，是**逐层否决**：L0 显著更差 → 停，不必跑 L1。

**这条在逻辑上是空的**：2-bit 的重构误差**必然**比 4-bit 大。用"显著更差"当否决条件，等于"2-bit 一律否决"，那就没有研究 2-bit 的必要了。审查指出"不同位宽误差天然有序"，正是这个意思。

### 4.2 改法：L0 从"关卡"降为"诊断"，否决权只保留给机制性病态

R2 已经确立了一条机制事实：**早层失败是方向错误，不是幅度错误**（只修幅度更差；只修方向回收 79%）。因为 RMSNorm 吸收幅度、不吸收方向。

据此，L0 的否决权只挂在**方向塌陷**上，不挂在误差大小上：

| L0 指标 | 角色 | 能否否决 |
|---|---|---|
| 逐输出行 `cos` 的**下尾**（如 1 分位） | 方向是否还在 | **能**：若下尾接近 0 或为负，说明该 tensor 的方向结构已被破坏，后续 L1/L2 无意义 |
| `rel_rms` 的**分布** | 幅度误差的量级与集中度 | 不能单独否决；用于解释 L1 的差异来源 |
| 逐元素相对误差的 99.9 分位 | 尾部是否爆炸 | 能，但需预注册阈值 |
| 每行 `max_abs_level` 直方图 / 饱和比例 | 是否大量行被钉在最高 level | 能，需预注册阈值 |
| 按 `q/k/v/o`、`gate/up/down`、`embed/head`、按层分组 | 定位 | 不能否决，只用于归因 |

**关键改动**：`rel_rms` 的绝对值与"比 Q4 差"**不再是判据**。它只回答"误差多大、集中在哪"。真正的关卡是 L1/L2 的**能力非劣性**，见 `2026-10-r5-stage-c-redesign.md`。

### 4.3 误差预算怎么写才不是拍脑袋

不能写"rel_rms < 0.1 通过"——这个数没有来源。可行的写法是把预算**锚在可观测的损伤标尺上**：

```
D4 = ΔNLL(Q4 vs BF16)   配对均值，同一批窗口
D2 = ΔNLL(Q2 vs BF16)
ρ  = (D2 − D4) / D4 = ΔNLL(Q2 vs Q4) / D4     ← 决策量，无量纲
```

- `ρ` 的 95% CI **上界 < 1** → Q2 的额外损伤不超过 Q4 相对 BF16 的损伤，**这是"可接受"的可操作定义**；
- `ρ` 的 CI **下界 > 3** → 明确越界；
- 中间 → **判为"未测出结论"**，不得写成"等价"。

1 与 3 这两个数是**人为选定并预注册**的，不是从理论推出来的——这一点必须写在报告里，不能伪装成推导结果。

## 5. E-R5-5（P2）XD-3 归因不能只看 1.91 / 1.15

### 5.1 接受

R4 §6.2 的归因规则是"同环境复现 1.91× → 代码；消失 → 环境"。这条规则**方向对，但证据不够**：两个 commit 之间如果有**多处**改动（mask 构造、chunk 大小、cache 初始化、调用签名），仅凭总时间比值无法定位，甚至无法排除"两处改动方向相反、部分抵消"。

### 5.2 补四项 artifact 级对照（在计时之前做）

| # | 对照 | 做法 | 判据 |
|---|---|---|---|
| **A1** | 固定输入 | 同一 `mx.array` ids、同一 seed、同一 dtype，落盘成 `.npy` 由两侧共同读取 | 两侧输入哈希必须相等，否则作废 |
| **A2** | mask 逐位比对 | 两侧各自 dump 实际送入 attention 的 mask（shape + dtype + 前 64×64 与全量哈希） | 形状或内容不同 → 差异来源即此处，不必再猜 |
| **A3** | 调用签名 diff | 记录每层/每组实际收到的 kwargs（是否传 `mask`、`cache`、`offset`、`dtype`），序列化成 JSON 做 diff | 签名不同 → 走的分支不同，先对齐再计时 |
| **A4** | 混合依赖图 diff | 打印实际执行的 block 序列与依赖边（不是配置里的 plan，是运行时真正跑的） | 图不同 → 工作量不同，时间不可比 |

**顺序很重要：A1–A4 全部一致之后，计时才有解释力。** 如果 A2 或 A4 已经不同，那么 1.91× 是"不同计算量"，不是"同一计算量的实现差异"，整个归因问题被替换掉。

### 5.3 profiling 作为第二证据

若 A1–A4 全一致而时间仍差 1.9×，再用：
- `mx.metal.start_capture()` 取 GPU trace（若可用），看 kernel 数与每 kernel 时长；
- 逐层计时（单层 `mx.eval` 前后打点），定位是"每层都慢"还是"少数层慢"；
- 检查是否有隐式 `mx.eval` 被插入（`mx.compile` 失效、`clear_cache` 频率变化）。

**这三项都不改变 R4 的结论边界**：跨轮绝对时间仍然不可引用；XD-3 的目的始终是"解释那两个数"，不是"给 M4 定性能上限"。
